# Fused int4 GEMV kernel: measured results

Device: **NVIDIA GeForce RTX 4060 Laptop GPU** (theoretical DRAM bandwidth 256 GB/s, measured streaming-read bandwidth 252 GB/s = 98% of theoretical, L2 32 MB). Every number below is the median of 5 independent benchmark invocations. Generated by `scripts/build_kernel_report.py` from `docs/results/`.

## What was built

A decode matvec `y = W_q x` with asymmetric group-wise int4 weights (group 128), fused so the fp16 weight matrix is never materialized. At batch 1 decode is memory-bound: runtime is set by bytes moved, so int4 should approach the byte ratio (about 3.76x with group-128 fp16 scales and zeros, not 4x) if the kernel saturates DRAM. The figures of merit are achieved bandwidth (against both the theoretical peak and the measured streaming-read bandwidth) and speedup against that byte-ratio ceiling.

Seven stages, each changing one thing (see `src/inferno/kernels/int4_gemv.cuh`, `int4_gemv_batch.cuh`):

| stage | change |
|---|---|
| v0 | one thread per row (uncoalesced) |
| v1 | one warp per row, coalesced 32-bit loads, shuffle reduce |
| v2 | 128-bit loads, activation vector staged in shared memory (predicted 16-way bank conflict: lanes fall on 2 of 32 banks) |
| v3 | v2 + one pad word per 32 activations (conflict-free) |
| v4 | v3 + algebraic form `s*(sum(q*x) - z*sum(x))`, streaming loads, 2 loads in flight |
| v5 | register reuse: decode the 32 weights of a chunk once into registers, read activations through the read-only cache (no shared-memory staging, no per-block prologue) |
| v6 | v5 with 16 lanes per row instead of 32 (K=1536 has 48 chunks per row: 32 lanes leave half of them with two chunks and half with one; 16 lanes give every lane exactly three) |

## Correctness

All kernels were checked against a double-precision CPU reference on every shape in every invocation before any timing was trusted: **all correct**, worst relative error 4.35e-04 (fp16 output rounding is ~5e-4). This gate mattered: the first version of v4 was flagged INCORRECT (relative error ~2-3) because it subtracted `z * sum(x over a whole 128-weight group)` once per 32-weight chunk, four times over; the bug was found and fixed only because timing was never reported for a kernel that failed the check. The kernel was additionally checked on the real Qwen2.5-1.5B-AWQ checkpoint inside vLLM (see the end-to-end section).

## What each stage bought (large, stable layers)

- **qwen1.5B_gate_up**: v0 to v1 2.9x faster (coalescing); v1 to v2 7.0% slower (wider loads + shared-memory staging, with bank conflicts); v2 to v3 9.1% faster (conflict-free padding); v3 to v4 17.2% slower (algebraic form, streaming loads); v4 to v5 19.0% faster (register reuse, no smem staging); v5 to v6 5.1% faster (16 lanes per row). Best: 93% of theoretical peak bandwidth.
- **qwen1.5B_down**: v0 to v1 16.8x faster (coalescing); v1 to v2 0.2% slower (wider loads + shared-memory staging, with bank conflicts); v2 to v3 5.6% faster (conflict-free padding); v3 to v4 21.7% slower (algebraic form, streaming loads); v4 to v5 30.5% faster (register reuse, no smem staging); v5 to v6 1.5% faster (16 lanes per row). Best: 87% of theoretical peak bandwidth.
- **llama7B_mlp_up**: v0 to v1 8.8x faster (coalescing); v1 to v2 2.8% slower (wider loads + shared-memory staging, with bank conflicts); v2 to v3 10.5% faster (conflict-free padding); v3 to v4 0.1% faster (algebraic form, streaming loads); v4 to v5 2.8% faster (register reuse, no smem staging); v5 to v6 0.2% slower (16 lanes per row). Best: 95% of theoretical peak bandwidth.

## Measurement notes and a correction

**Weight-rotation size.** Each launch must stream its weights from DRAM, so the benchmark rotates through many copies of them. The first version rotated through 192 MB (6x L2). Sweeping the footprint showed that this was not enough: an L2 with non-LRU replacement keeps part of a cyclic working set, and a 23 MB kernel ran about 6% too fast. Every earlier '% of peak' figure was inflated by that amount. The default is now 768 MB (24x L2).

| rotation footprint | v5 on llama7B_mlp_up (us, 3 runs) | cuBLAS fp16 (us, median of 3) |
|---|---|---|
| 192 MB | 92.9, 93.0, 93.0 | 360.4 |
| 384 MB | 93.2, 93.2, 93.3 | 361.0 |
| 768 MB | 98.2, 98.9, 99.0 | 360.9 |
| 1536 MB | 98.4, 98.3, 98.3 | 360.9 |

**Achievable bandwidth.** A read-only streaming kernel over a 512 MB buffer reaches 252 GB/s (98.3% of the 256 GB/s computed from the reported memory clock). The table reports both denominators; the achievable figure is the honest ceiling for a read-bound kernel.

Reading this honestly:
- vLLM's Marlin kernel is at or near the bandwidth limit for the large layers at batch 1 on this GPU. The custom kernel is within roughly 15% of it on the large layers in CUDA-graph decode and about even on the small ones; it is faster than the classic AWQ kernel on every layer; it does **not** beat Marlin. End-to-end throughput (below) is the more reliable summary: parity at one sequence.
- **Correction.** An earlier version of this report claimed the custom kernel beat Marlin on all four layer shapes, from a Marlin timing about twice as slow as the values above. That timing cannot be reproduced: re-measuring Marlin in the same session in both eager and CUDA-graph mode gives the values in the table, and end-to-end throughput agrees with them. The earlier measurement is treated as invalid and its file has been retired.
- **Likely cause of the bad sample.** 2 of the 18 in-situ profiling processes run for this report had every kernel, FlashAttention included, running 2-5x slower than in sibling processes (a GPU-wide slowdown such as throttling). A single-process measurement taken during such an episode would look like the retracted one. This is why each in-situ time is the median of three fresh processes. It cannot be verified for the old run.
- In-situ times still vary between processes and between engine modes by more than the differences between the custom kernel and Marlin on some layers (see the ranges in `docs/results/insitu/*.json`), and the custom kernel's mode dependence (for example gate/up in eager vs graph mode) is larger than Marlin's and points the other way. The cause is not established; one hypothesis is that the custom kernel, which spends more instructions per weight, is more sensitive to SM clock and power state than a purely memory-bound kernel.

## Experiments that did not help (development log)

Single-invocation development measurements on the Qwen gate_up shape (17920x1536) unless noted; kept because negative results constrain the explanation.

- **v4 lost to v3 on the Qwen layers (K=1536, K=8960) but won on the Llama-7B shape (K=4096).** Hypotheses tested and rejected:
  - *Streaming (evict-first) loads hurt short rows*: swapping to ordinary loads left gate_up unchanged (81.5 us vs 81 us) and made the K=4096 shape slower, so streaming loads are kept.
  - *Per-block prologue*: a variant that precomputed per-chunk sums of x in shared memory was slower (85 us); parallelizing that prologue with warp shuffles was slower still (106 us), because a shuffle reduction is a chain of dependent ~25-cycle operations. Removing the prologue by accumulating sum(x) inside the main loop recovered most of the loss (81 us) but not all of it.
  - *Late issue of scale/zero loads*: hoisting them to the top of the loop moved gate_up from 80.9 to 79.7 us, within noise.
- **What worked (v5, v6).** Dropping the shared-memory staging entirely (read activations through the read-only cache, decode each weight chunk once into registers) removed the K=1536 slowdown, and using 16 instead of 32 lanes per row helped the K=1536 layers a further 4-15% in the same invocation. That is consistent with the two candidate explanations (shared-memory prologue, lane imbalance for 48-chunk rows), but no profiler counter has confirmed which one is responsible.
- **Unrolling did not help.** Loading 2-6 chunks per lane before consuming them (more loads in flight) never beat one chunk per iteration once the lanes were balanced (`bench_int4_gemv --variants`).
- **Still unexplained and unconfirmed:** the bank-conflict prediction for v2/v3 and the exact cause of the v4 slowdown. Separating them needs Nsight Compute counters (`make kernel-profile`), which require enabling GPU performance counters in the NVIDIA Control Panel on Windows (`ERR_NVGPUCTRPERM` otherwise; re-checked and still blocked). Until then these remain hypotheses.

## Limitations

- Batch 1 and very small batches only; above B of about 8 a tensor-core kernel is needed.
- Measured on one laptop GPU (sm_89, 24 SMs, 256 GB/s). Numbers on other devices will differ; the `ARCH` variable in `src/inferno/kernels/Makefile` targets others.
- Small layers are dominated by jitter; only large-layer conclusions are drawn.
- In-situ times are kernel times only; the end-to-end section covers whole-token decode for one model on one GPU.
- No Nsight counters (blocked by a Windows driver setting), so causal explanations are hypotheses.
