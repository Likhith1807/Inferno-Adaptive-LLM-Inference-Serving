# Methodology

## Question and hypotheses

Can a load- and length-aware routing policy over pre-loaded heterogeneous replicas beat every fixed
configuration under realistic LLM traffic, and what does that show about where HPC and AI systems meet?

| ID | Statement | Where it is tested |
|----|-----------|--------------------|
| H1 | Adaptive p99 latency is lower than the best fixed configuration at non-inferior throughput under bursty / mixed-length load | `run_full_campaign` + `report` |
| H2 | MPI multi-replica routing scales sub-linearly; coordination overhead is measured and grows with replica count | `run_scaling`, `mpi_router/microbench` |
| H3 | A hand-written fused int4 GEMV reaches a fraction of the vendor path; the gap is explained by profiler counters | `kernels/bench_int4_gemv` + Nsight |
| H4 | Systems-level adaptivity, not model changes, drives tokens-per-joule / cost-per-token gains | power columns, ablation tables |

## Variables

**Independent:** routing policy (fixed-fast, fixed-bulk, static load balancer, adaptive), quantization level
(fp16 / int8 / int4), router type (HTTP vs MPI), replica count, load pattern (steady, bursty, mixed-length).

**Dependent:** TTFT, TPOT, end-to-end p50/p95/p99, throughput (output tokens/s), goodput under an SLO,
GPU power, energy, tokens per joule, peak GPU memory, per-hop MPI overhead, kernel time and achieved DRAM bandwidth.

**Controlled:** model family and tokenizer, hardware, seeded request streams (repetition *k* is byte-identical
across policies), output length pinned with `ignore_eos`, GPU memory residency (all replicas of a pool are loaded
for every policy).

## Design of the adaptive comparison

vLLM cannot change `max_num_seqs` or quantization on a live server. Adaptation is therefore **routing across
pre-loaded configurations**. Fixed baselines run in the *same* pool with the same memory residency, so the
adaptive policy cannot win by handing the baseline a different hardware situation.

The controller (`controller/routing_policies.py`) has three levels (calm, pressured, overloaded), escalates on
tier-0 utilization or a TTFT p95 breach, and de-escalates only after several consecutive calm ticks
(hysteresis). Every tick is logged with a reason string so decisions can be audited and plotted.

## Statistical protocol

- Every cell is repeated (default 8). Headline numbers are mean ± 95% CI (t-distribution).
- Adaptive vs best-fixed is a **paired** comparison (same seeded stream per repetition). "Best fixed" is chosen
  per load pattern on the same metric being tested, among configurations with zero errors: the strongest baseline
  available.
- Tests: paired t-test and Wilcoxon signed-rank; a result counts as significant only if both agree and the
  Holm-adjusted p (across load patterns) is below 0.05. Effect size (Cohen's d_z) and a bootstrap CI of the paired
  difference are reported.
- A throughput non-inferiority check (>= 98% of best-fixed) guards against "wins" that trade away capacity.
- Policy order within each repetition is shuffled with a recorded seed to cancel thermal drift (laptop GPUs
  throttle) and cache effects.
- Verdicts are generated by code (`analysis/aggregate.verdict`) and include "no significant difference" and
  "adaptive WORSE" outcomes.

## Measurement discipline

- **Open loop.** Requests are sent at their scheduled time regardless of completions; latency is measured from the
  scheduled arrival, so server-side queueing is counted.
- **Warmup excluded.** Requests scheduled during the warmup window, and a pre-run warmup burst, are dropped.
- **Kernel timing.** Weights rotate through at least 24x the L2 size (768 MB), so each launch streams from DRAM
  (192 MB / 6x L2 was tried first and leaked ~6% through a non-LRU L2; see lesson 8); timings are batches of
  back-to-back launches, reported as median / p10 / p90 over 5 fresh invocations, with the number of runs within 2% of
  the median. Correctness against a double-precision CPU reference is checked before any timing is trusted.
- **Bandwidth references.** Results are reported against the theoretical peak (from the memory clock) and against a
  measured streaming-read bandwidth (a read-only kernel over 512 MB).
- **In-situ and end-to-end.** Library kernels are timed inside vLLM decode with torch.profiler under both eager and
  CUDA-graph modes, in 3 fresh processes (median across processes); end-to-end decode throughput is measured in fresh
  processes with CUDA graphs, 3 repetitions in rotated configuration order, and the token streams are compared.
- **Effective bandwidth** counts only bytes that must cross DRAM (packed weights + scales + zeros + activations +
  outputs), and is compared with the device's theoretical peak. Cross-kernel comparisons across different byte
  counts use time, not bandwidth.
- **Power.** `nvidia-smi` streaming samples at 200 ms, trapezoidal energy, summed across GPUs on multi-GPU runs.
- Every run directory contains `hardware.json` (GPU, driver, package versions, commit) and `config_snapshot.json`.


## Lessons that changed the protocol (found by running it)

1. **Load is defined relative to measured capacity, not guessed.** A first smoke run at a guessed 4 req/s was
   already saturating the GPU (p99 35 s, 0% SLO attainment), which says nothing about policy quality.
   `experiments/calibrate.py` saturates a reference replica, measures tokens/s per length profile, and derives every
   pattern as a fraction of capacity (steady 0.6x; bursty base 0.35x and bursts at 1.5x; mixed 0.6x of its own capacity).
2. **Throughput counts the drain.** Dividing completed tokens by the arrival window made every policy that eventually
   finished report the offered load. Throughput is now tokens over the busy span (arrival window or time to last
   completion, whichever is longer); the offered rate is reported separately.
3. **Statistical power sets the minimum repetitions.** A Wilcoxon signed-rank test with n pairs cannot go below
   p = 2/2^n (0.0625 at n=5). With Holm correction across three load patterns the smallest attainable adjusted p is
   3 x 2/2^n: 0.047 at n=7 (under 0.05 but with no margin) and 0.023 at n=8. Seven pairs is therefore the theoretical
   minimum and eight was used because it leaves headroom. Smaller studies (n=4-5) are
   labelled as unable to detect small effects, and effect sizes and CIs are reported instead.
4. **Which library kernel is in use is part of the experiment.** vLLM with `quantization=awq` runs the original AWQ
   kernel; `awq_marlin` runs Marlin. They differ 2.1x in server-level throughput on this GPU. Serving configs pin
   `awq_marlin` / `gptq_marlin` explicitly, and the kernel comparison measures both.
5. **A correctness gate must precede timing.** The first fast version of the v4 kernel was wrong by ~2-3x relative
   error; only the CPU-reference check caught it. Timing is never reported for a kernel that fails.
6. **Interim looks are not results.** Early campaign numbers suggested the adaptive policy was 3x worse; that was
   recorded as a hypothesis about co-residency and tested with a controlled experiment (`run_contention.py`)
   before any conclusion was drawn.
7. **Bounded drain for low-capacity configurations.** Sweep runs cancel requests still unfinished 60 s after the last
   arrival and record them as failures, so a configuration far below the offered load cannot stall the sweep and its
   completion rate stays visible.

8. **A bandwidth above 100% is a bug report.** One kernel measured above the theoretical peak; a sweep of the
   weight-rotation footprint showed a 192 MB rotation let the L2 serve ~6% of the traffic. Default raised to 768 MB and
   every kernel number regenerated.
9. **Close every kernel comparison at a second level of measurement.** A library-kernel timing (Marlin, ~2x too slow,
   irreproducible) had made the custom kernel look faster than Marlin on 4 of 4 shapes. End-to-end tokens/s disagreed
   with it; re-profiling all three paths together in both engine modes gave the true picture (Marlin is at the bandwidth
   limit at batch 1). The claim was retracted and the file retired. In-situ timings are also taken in 3 fresh processes
   because single processes differ by ~10%.
10. **Check headroom before running the next experiment.** The best single fixed tier is within 3.3% of the per-pattern
    best, so a second adaptive-routing campaign on the shared GPU could not have shown a meaningful win; it was not run.

## Honesty checkpoints

1. If the custom kernel loses to the library path, the ratio is reported (it is at parity with Marlin at one sequence and slower with concurrency) and explained with profiler counters where those can be read (currently blocked).
2. If MPI overhead erodes gains, the crossover replica count is shown.
3. Where the adaptive policy does not help (for example steady load, where a tuned fixed configuration should
   match it), the report says so; the verdict text is produced by code and does not depend on the author's hopes.
4. Threats to validity: single-GPU contention between replicas (local study), synthetic prompt text, quantized
   checkpoint quality not evaluated, one model family.
